# The app layer

The files directly under `src/` and in `src/routes/` sit where @solidjs/vite-plugin and filesystem-routing expect them. They are not a feature: they stay thin, wire the framework, and delegate to the feature folders (`src/design`, `src/shell`, `src/planner`, `src/mcp-server`). They may import any feature's `index.ts` and nothing deeper (`tools/repo-checks`, ADR 0008). The root config files (`vite.config.ts`, `env.ts`, `vitest-setup.ts`, `vitest-env-server-stub.ts`, `oxlint.config.ts`) belong to the same layer; their notes are in the repo `README.md` under "Configuration".

## Files

- `App.tsx`: the app component the plugin wraps in `Document.tsx`. It loads the stylesheets in cascade order by importing the features (`./design` for the tokens, the components and the gallery; `./shell` for the page frame; `./planner` for the planner), and renders each route inside the `Shell` under the router.
- `Document.tsx`: the document shell, the replacement for `index.html`, picked up by the `src/Document.*` convention. It must render the full `<html>`. `<HydrationScript />` activates under `ssr: true`; the static site (`pages` mode) prerenders this shell once to `index.html`, where the plugin strips the script. The favicon is named under Vite's base, so it loads under the site's `/wotr-planner-solid2/`.
- `router.ts`: the router lives in its own module so `App.tsx` (rendering) and `server-config.ts` (the single-flight collector) share one instance. Its `base` is Vite's (`import.meta.env.BASE_URL`): `/` for the server, `/wotr-planner-solid2/` for the static site, so routes and `paths()` sit under it. Link preloading is opt-in; `intentPreload()` is the hover, focus and touch strategy: resting on a link warms its code and runs its preload, which makes navigation feel instant once data lives on the server.
- `server-config.ts`: the pre-dispatch server-function configuration, pinned into the handler graph by `serverFunctions.serverSetup` in `vite.config.ts`, so it loads before any dispatch on the dev middleware and the production handler alike. Registering the router as the single-flight collector turns a mutation into one round trip: the action response carries the refreshed `query()` data for the page the client will show (the collector reruns that route's preloads on the server), and the router seeds its cache from that envelope instead of refetching.
- `middleware.ts`: the server middleware chain, wired through `start.middleware` in `vite.config.ts`. Each function is `(event, next) => Response`: the request is `event.request`, and `next()` takes no arguments, so assign `event.request` before calling it to hand a different request downstream. Per-request render inputs (`event.nonce`, `event.renderMode`) go on the event before `next()` too, since the page render runs inside it. The chain fronts every request the server dispatches (page renders, server function calls and API routes) and runs inside the request-event scope, so `getRequestEvent()` and the session helpers work there as in application code. Its one member, `createAPIHandler`, serves the `GET`/`POST`/… exports of route modules and passes everything else down the chain; it takes the request event and hands that same event to the handler, with the matched params written onto it.
- `vite-env.d.ts`: the ambient types: Vite's client types, the plugin's boundary modules, the generated file-route types, and `virtual:data-document`, whose default export is the path of the data document (`vite/data-document`): `{ files, overrides }` as one content-hashed JSON file.

## Routes

- `routes/index.tsx`: the planner's page. There is one page, at `/`, with the Build in the fragment as `#b=<Build code>` (map 13).
- `routes/design.tsx`: the design gallery at `/design` (`src/design`, build ticket 05a).
- `routes/mcp.ts`: the MCP over streamable HTTP at `/mcp` (map 08, build ticket 05). It is stateless: one server and one transport per request, answering in JSON (`src/mcp-server`). `bun start` serves it through the `createAPIHandler` middleware. The handler is exported as `POST`, `GET` and `DELETE` constants, because filesystem-routing finds a route's HTTP methods by scanning its exports.
- `routes/[...404].tsx`: the catch-all route. `httpStatus(404)` sets the response status during SSR (a no-op in the browser); it runs in the route's `preload` so the status is set before the response head flushes.
